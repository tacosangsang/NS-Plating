# 02. 작업 규칙과 의사결정

## 1. 사용자 규칙 핵심 (매번 읽는 10줄)

1. 한국어로 답하고 이모지를 쓰지 않는다. 요청한 범위만 한다. 비판적·객관적으로 말하고, 확실하지 않으면 추측하지 않고 묻는다. `[예외: 사용자 소통 취향]` 한국어·이모지 금지는 이 사용자 고유. "범위만, 추측 금지, 반박 허용"은 일반 규칙으로 가져갈 가치가 있다.
2. 크레딧이 드는 생성·edit은 사용자가 "생성해"라고 한 뒤에만. 결과는 아티팩트로 먼저 보여 주고, OK를 받은 뒤 드라이브에 저장한다. 사용자가 손본 파일은 사용자가 올린다.
3. 생성 입력은 가장 화질 좋은 원본만. 축소본·편집기 내보낸 판은 쓰지 않는다.
4. 코드로 되는 수정(색·밝기·자르기·합성·크기)은 코드로. 편집본을 또 편집하지 않고 원본에서 다시 한다.
5. 이미지는 Seedream Pro. 시트는 흰 배경, 그림자·글씨 없음, 어떤 요소도 잘리지 않음. `[예외: 모델 선택은 프로젝트 계정·스타일 결정]` 시트 규격(흰 배경·안 잘림)은 일반.
6. 스톱모션·클레이·인형 단어는 부정문으로도 쓰지 않는다. 실사 연상 단어·실사 결과물을 입력으로 쓰지 않는다. `[예외: 3D 애니메이션 룩 결정 — 부정문도 끌려간다는 함정 자체는 일반]`
7. 도면·확정 시트 > 컷표 수정 토글 > 시나리오. 애매하면 묻는다. 블록아웃 기반 그림은 기준 버전을 확인한다.
8. 영상 액팅은 컷표 해당 컷 문장을 먼저 읽고 쓴다. 비트마다 원인이 앞에 온다.
9. 코드로 고친 입력 이미지·영상 조각은 원본 해상도 다운로드 페이지로 준다. 프롬프트 문서 섹션 제목 끝에 상태 꼬리표를 단다.
10. 사람용 본문(노션)에는 날짜·출처·버전 꼬리표를 쓰지 않는다. 그런 정보는 AI용 md에만.

## 2. 소통·결과물 규칙

### 소통
- 확정되지 않은 설정을 임의로 좁혀 가정하지 않는다. 가정이 필요하면 "내가 정한 것"으로 표시하고 근거를 쓴다.
- 수동 작업을 부탁하기 전에 자기 도구 목록부터 확인한다. 실패하면 호출한 도구 이름과 오류를 그대로 보고한다(요약·해석 금지).
- 피드백은 비판적으로. 사용자 추론에 허점이 있으면 지적한다. 동의하기 위해 동의하지 않는다.
- 같은 작업을 비효율적으로 반복해야 하는 상황(설정이 없어서 등)이 생기면 멈추고 문제와 해결 방법을 먼저 보고한다.

### 승인 어휘 (크레딧이 드는 일)
- "생성해", "돌려": 생성 승인.
- "~하자"(예: "두 개 합쳐서 하자"): 프롬프트 작업 지시이지 생성 승인이 아니다(11-02). 생성 직전에 프롬프트를 보여 주고 크레딧을 한 줄로 묻고 답을 기다린다.
- "씬 하나 다 만들어 둬": 그 씬 한 바퀴 생성은 승인된 것(09 문서 AI 단독 작업).
- 사용자가 edit을 고르면 위험을 말하고 생성안도 같은 턴에 준비해 둔다.

### 결과물
- 작업물·렌더·검수 결과는 언제나 아티팩트 하나에 모아서 보여 준다. 실패한 결과도 이미지로 보여 준다.
- 결과를 보여 준 뒤 다음 단계(드라이브 저장·추가 생성)로 넘어간다. 보여 주지 않고 저장하거나 글로만 요약하고 다음 생성을 제안하면 지적받았다(11-02).
- 이미지 박힌 아티팩트는 약 4MB부터 수정이 안 된다. 그때는 새 페이지(링크 바뀜을 알린다). 아티팩트 안 이미지는 1600px 축소본이라 입력으로 쓰지 않는다.
- 코드로 자르거나 고친 입력 이미지는 축소 없이 원본 해상도 다운로드 버튼이 있는 아티팩트로 바로 준다. 경로만 알려 주지 않는다(사용자가 웹앱에 바로 올려 쓴다, 11-04). 영상 조각(숏별로 자른 클립, edit 입력)도 같다. 일반 `<a download>`는 아티팩트에서 동작하지 않아 downloads capability(fetch → blob → save)를 쓴다.
- 결과 파일은 드라이브, 안 되면 ZIP. 사용자가 직접 손본 파일은 사용자가 올린다(Claude가 다시 올리면 중복, 10-25).
- 프로젝트 공유 폴더 첨부는 약 400MB까지는 되고 약 660MB는 실패한다. 2K ProRes HQ는 약 25MB/초라 16초 넘는 클립은 처음부터 나눈다(11-06).

### 이미지·시트
- 기본 모델은 Seedream. 지정이 없으면 GPT Image를 쓰지 않는다. `[예외: 프로젝트 모델 결정]`
- 시트 프롬프트에 "전체가 프레임 안, 네 변 모두 흰 여백, 어떤 부분도 가장자리에 닿거나 넘지 않음(entire subject fully inside the frame, white margin on all four sides, nothing touching or crossing the edges)"을 넣는다. 잘린 부분은 코드로 되살릴 수 없어 재생성해야 한다(11-01).
- 가장자리 잡티처럼 되돌릴 수 있는 코드 보정은 묻지 말고 먼저 하고 한 줄 보고. 형태·설정·색 기준이 바뀌는 것만 묻는다(10-16).
- 3000자 제한은 이미지 프롬프트에만(공통 블록 포함). 영상 프롬프트는 제한 없음(10-28). `[예외: 사용 모델의 제한 — 숫자는 모델마다 다름]`
- 입력 이미지는 본문에서 @image1, @image2로 지칭한다. 시작 프레임도 "Start frame"이라고만 쓰지 않고 @image 번호를 붙인다. 입력 영상은 @video. 옛 표기 `@[이미지 1](image_1)`, "IMAGE 3", "이미지3"은 쓰지 않는다(10-10, 10-31, 11-03). 왜: 같은 프롬프트를 여러 도구(AICRON은 image_urls 순서가 곧 번호)에서 쓴다.
- 상류층은 낡거나 헐렁하게 그리지 않는다. `[예외: 설정]`
- 캐릭터 통합 시트에 팔레트를 넣지 않는다(10-09). `[예외: 사용자 시트 취향]`

### 영상
- 컷 길이를 균일하게 하지 않는다. 러닝타임에 맞춰 줄이지 않는다. 음악 없음. `[예외: 연출 결정 — "균일 금지"는 일반적으로도 유효]`
- 씬 하나씩 천천히 검수한다. 매 수정 뒤 앵글·구도·액팅·컨티뉴이티를 다시 본다.
- 영상 생성은 480p로 하고 1080은 나중에 업스케일(11-06). 길이는 크레딧 부족이라 필요한 만큼만(최대 30초). `[예외: 크레딧 사정]`
- 프롬프트가 굳으면 컷표에 초수·디테일을 반영한다.

## 3. 고칠 때 무엇으로 하나

| 바꿀 것 | 먼저 | 그다음 | 쓰지 않음 |
| --- | --- | --- | --- |
| 색·밝기·크기·위치·자르기·합치기 | 코드 | | 재생성 |
| 사람·소품 크기·위치(이미지) | 배경만 생성 + 코드 합성(원근 계산, 03 문서) | 깨끗한 배경에서 다시 Combine | 결과를 Edit |
| 형태·구조·새 뷰(이미지) | 원본(첫 생성본·블록아웃 렌더)에서 다시 | | 편집본 재편집 |
| 영상 외형(질감·소품·배경) | 카메라 고정 컷이면 사용자 합성 | 웹앱 video_edit, 컷마다 1장씩(06 문서) | 여러 컷 한 번에 배정 |
| 영상 동작·연기·구도(움직임 횟수·크기 포함) | 이음 프레임을 시작 프레임으로 그 구간만 새 생성 | | edit |
| 영상 속 작은 흔적 | 애프터이펙트 Content-Aware Fill | edit | |

편집 전 판단 순서(11-03): (1) 더 앞 단계 원본에서 여러 수정을 한 프롬프트에 묶어 한 번에 할 수 있는가, (2) 사용자가 직접 고칠 수 있는 소스(블록아웃 파일, 레이어 원본)가 있는가, (3) 코드 합성으로 되는가. 큰 차이가 없으면 원본 쪽. 체인이 불가피하면 몇 번째 편집인지 파일명과 보고에 적는다. 왜: 편집을 거칠수록 질감 뭉개짐·무늬·소품 크기 오차가 쌓인다.

부분 삭제의 기본형(11-05): Edit 결과에서 지울 영역(가장자리 6px 블러)만 잘라 원본 위에 코드로 합성. 나머지 픽셀은 원본 그대로. Edit은 전체를 다시 그려 다른 부분도 바뀌기 때문.

## 4. 크레딧 쓰기 전 점검 8줄

생성·edit 버튼 누르기 전에 매번. 걸리는 것이 있으면 프롬프트와 함께 먼저 말한다. 11-04 S#02에서 이 항목들이 빠져 생성을 여러 번 다시 했다.

1. **edit인가 새 생성인가 코드 합성인가.** 동작·연기·구도를 바꾸면 새 생성(앞 영상의 이음 프레임을 시작 프레임으로 그 구간만). 외형만 바꾸면 edit. 카메라가 고정이면 코드 합성이 더 싸고 확실하다.
2. **나눌까.** 하나라도 있으면 둘로 나누자고 먼저 제안: 레퍼런스 6장 이상(안전선 3~5장) / 한 생성 안의 하드컷(특히 뒤 숏에 시작 프레임이 없을 때) / 여러 이미지를 컷마다 배정해야 할 때 / 실패하기 쉬운 짧은 비트(1초 안의 손 동작, 작은 물체 이동)가 몰릴 때. 초 단가가 같아 비용은 거의 같고 실패한 쪽만 다시 돌린다(15초 = 10초 + 5초).
3. **중요 소품에 시트가 붙었나.** 핵심 소품은 시트를 붙인다. 한 시트에 종류가 여럿이면 하나만 원본 최고화질에서 잘라 넣는다(둘 있으면 랜덤). 같은 소품이 여러 생성에 나오면 글 묘사도 전부 같게.
4. **컷표 문장과 맞나.** 액팅은 컷표 해당 컷 문장을 먼저 읽고 쓴다. 다르게 쓰지 않는다.
5. **비트마다 원인이 앞에 있나.** "무엇을 보고, 무엇 때문에 → 이 동작". 반응이 원인보다 먼저 나오면 동기가 안 읽힌다.
6. **앞뒤 클립이 이어지나.** 앞 클립 끝 상태(누가 무엇을 들었나, 소품 위치)와 다음 클립 시작 프레임을 나란히 본다. 같은 물건을 두 번 주거나, 음식이 바뀌거나, 소품이 반대쪽이면 고친다.
7. **입력 파일이 가장 큰 원본인가.**
8. **해상도와 비용.** 처음 시험은 480p(또는 싼 모델), 굳은 뒤 1080p. 1080p로 바로 뽑으려 하면 실패할 만한 곳과 비용(1080p 81 Crons/초, 480p 20)을 같이 적는다. `[예외: 단가는 AICRON Seedance 2.5 기준]`

프롬프트 문서 섹션마다 프롬프트 바로 위에 **점검 결과 칸**: 위 8줄을 예/아니오/해당 없음으로, 아니오면 이유·대안 한 줄.

## 5. 결정은 사람이, 제안은 AI가

- 사용자가 확정한 치수·설정만 반영한다. AI가 제안한 값은 "가정"으로 표시하고 확인을 받는다.
- 사용자 선호 충돌을 발견하면 숨기지 않고 미결로 적는다. 예(PLATING): ponytail 스킬의 "요청 없는 추상화 금지"와 사용자 선호(Interface/abstract class) 충돌은 미결로 둠.
- 의사결정이 목표를 바꾸는 것이면 선택지와 추천을 한 번에 제시하고, 추천안으로 작업을 이어 간다(되돌릴 수 없는 단계만 멈춘다).
