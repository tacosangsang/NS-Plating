# 01. 문서 체계와 기록 규칙

## 1. 살아 있는 문서는 셋만

| 역할 | PLATING에서는 | 다른 프로젝트로 옮길 때 |
| --- | --- | --- |
| 이야기(내용) 정본 | 노션 시나리오 4차 | 기획서·스크립트 한 개 |
| 실행 단위 정본 | 노션 스토리보드/컷표(씬별 "S#XX 수정" 토글이 최우선) | 태스크 표·컷표 한 개 |
| 작업 방법 정본 | 작업 핸드북(노션 페이지 본문 + 맨 위 첨부 md) | 규칙·워크플로우 문서 한 개 |

- 셋 말고 나머지(옛 DB, 초안 페이지, 구글 시트, 이전 차수 시나리오)는 **백업본**이라고 문서에 못 박는다. 고치지 않고 참고만 한다. 백업본은 옛 번호 체계를 그대로 둔다(번호 재정렬 안 함).
- 새로 정해진 내용은 내용 정본에, 방법·규칙은 방법 정본에. 한 사실이 두 곳에 있으면 어느 쪽이 정본인지 적는다.
- 충돌 순서를 문서 맨 앞에 적는다. 예(PLATING): 도면·확정 시트 > 컷표 수정 토글 > 시나리오 4차 > 백업본. "확정본"이라고 적지 않은 것은 전부 임시본.
- 같은 페이지를 두 작업자(스레드)가 동시에 고치면 덮어쓴다. 범위를 단위(씬)별로 나눠 고친다.

## 2. 사람용 본문과 AI용 전체판을 분리

- 노션 본문 = 사람용. 날짜·출처·버전 꼬리표("(사용자 11-04)", "(블록아웃 v32 기준)")를 쓰지 않는다. 읽기를 방해한다.
- 맨 위 첨부 md = AI용 전체판. 날짜·출처·근거·실패 이력 전부 여기에. "이 파일 하나만 넘겨도 작업할 수 있게" 쓴다. 안 열리는 링크(아티팩트·드라이브)는 참고용으로만 두고, 없어도 작업이 되게 쓴다.
- 첨부는 교체가 안 되므로 새 md를 맨 위에 올린다. 읽는 쪽은 반드시 맨 위 판을 기준으로 한다. `[예외: 노션 첨부 파일 교체 불가라는 도구 제약]`
- 파일 이름에 날짜와 판(`_2026-11-05b.md`)을 넣는다. 로컬 사본 폴더에도 같은 이름으로 둔다.
- `[예외: 노션 PNG 업로드 차단, SVG만 가능 — 플랜 제약]` 그림이 필요하면 SVG로 만든다.

## 3. "꼭 읽을 것" 장 패턴

규칙 문서 맨 앞(0-1부)에 약 60줄짜리 필수 장을 둔다. 모든 작업자·AI가 매번 전부 읽고, 나머지는 하는 일에 맞는 장만 본다. 구성:

1. 사용자 규칙 핵심 10줄 (02 문서 참고)
2. "고칠 때 무엇으로 하나" 표 (02 문서)
3. 크레딧 쓰기 전 점검 8줄 (02 문서)
4. 기록하는 법 (아래 4절)

왜: 11-05 점검에서 실패 7건(약 924 Crons) 중 4건이 이미 다른 장에 적힌 규칙을 못 봐서 생긴 것이었다. 규칙을 더 적는 것보다 읽게 만드는 구조가 효과가 컸다.

읽는 순서를 문서 첫머리에 명시한다. 예(PLATING): 이미지 생성은 3부, 블록아웃은 3-1부, 연출 설계는 3-2부, 스타일 블록은 4부, 영상은 5-3·5-4·5-6장, 업스케일은 5-10장, edit은 5-11장, 외부 AI(Codex)는 5-12장부터.

## 4. 기록 규칙 (누가 무엇을 언제)

사용자 11-05 결정, 개선안 1~4 전부 승인.

1. **작업 스레드는 새 교훈·결정을 프로젝트 메모리에만, 배운 그 턴에 적는다.** 주제별 파일에 덧붙인다(파일 하나에 사실 하나가 아니라 주제 하나).
2. **규칙 문서(핸드북 md·노션 본문)는 담당 스레드 하나만 고친다.** 하루 한 번 메모리와 최근 스레드에서 확정된 것을 모아 새 md를 올린다. 다른 스레드는 손대지 않는다(덮어쓰기 충돌 방지). 급한 규칙은 메모리에 적고 해당 스레드에 알린다.
3. 그래서 규칙 문서는 최대 하루 늦다. 작업 전에 메모리 색인(MEMORY.md)을 같이 본다.
4. **프롬프트 문서는 섹션마다 프롬프트 바로 위에 "점검 결과 칸"**을 둔다(02 문서 점검 8줄을 예/아니오/해당 없음으로). 빈 칸이면 승인을 기다리지 말고 먼저 채운다.
5. **생성 원본은 받자마자 `video/<씬>/raw/`에 원래 이름 그대로.** 업스케일·edit 입력·프레임 대조는 전부 여기서 시작한다. 편집기에서 내보낸 파일은 raw에 넣지 않는다.

## 5. 상태 꼬리표

- 프롬프트 문서의 ##/### 제목 끝에 상태를 단다: `[최신]`, `[옛 판, 쓰지 않음 → 대체 섹션 이름]`, `[실패, 쓰지 않음]`, `[완료]`. 새 판을 만들면 같은 턴에 옛 판 꼬리표를 바꾼다. 왜: 한 파일에 같은 생성의 여러 판(15초판·10초+5초판, E3와 E3-1~4)이 쌓여 어느 것을 복사할지 헷갈렸다(11-04).
- 블록아웃에서 나온 렌더·시트는 파일명에 기준 버전 접두사(`v22_`)나 README 기준 버전을 남긴다. 버전 없는 그림은 구조 레퍼런스로 쓰지 않는다(04 문서).
- 사용자가 파일과 함께 "확정본"이라고 명시한 것만 확정. 첨부 이미지를 메모리나 노션에 임의로 "확정"이라 적지 않는다(10-08).

- 사용자 PC: `D:\Plating`(블록아웃·변환 스크립트), `G:\내 드라이브\RAPA-NS_PLATING`(드라이브 동기화).
