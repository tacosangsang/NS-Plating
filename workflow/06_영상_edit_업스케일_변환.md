# 06. 영상 edit, 업스케일, 편집용 변환

## 1. edit을 쓸 때와 못 쓸 때

| 상황 | 방법 |
| --- | --- |
| 액팅·카메라·컷 타이밍이 맞는 영상이 있고 **외형만**(질감·소품·배경) 바꿀 때 | edit |
| 동작·구도·동선이 틀림 | 새 생성. edit은 입력 영상의 움직임을 따라가 틀린 동작도 그대로 남는다 |
| 연기·동작 변경 | edit 불가(11-04 실증: 구슬 굴리기 → 손가락으로 밀기 edit 3초 330 Crons가 원본과 똑같이). 원본 이음 프레임을 시작 프레임으로 그 구간만 새 생성해 붙인다 |
| 기존 움직임의 횟수·크기 변경("2~3번 펄럭이게") | edit 불가(11-05, 구조를 바꿔 3번 돌려 모두 원본처럼 한 번). 그 구간만 시작·끝 프레임 새 생성 |
| 물체가 떠나거나 생기는 등 화면 내용이 바뀌는 사건("포스터가 떨어져 날아감") | edit 됨(매번) |
| 작은 소품 추가(480p 기준 약 28px 라디오) | edit 잘 됨. 단 밝기는 시트를 따라 떠 보이니 편집기 마스크 색보정 필요하다고 미리 말한다 |
| 카메라가 고정된 컷의 배경·소품 교체 | 사용자 합성이 더 싸고 확실. edit 전에 먼저 제안 |
| 화면 속 작은 흔적만 지우기 | 애프터이펙트 Content-Aware Fill. edit은 모든 프레임을 다시 그려 매듭·손가락이 조금 바뀐다 |
| 카메라 움직임 변경 | edit 불가 → 새 생성 |

추정 원리: edit은 "화면 내용이 바뀌는 사건"은 받고, "기존 동작을 늘리거나 반복"은 입력 움직임을 따라 무시한다.

`[예외: 컷표에서 사용자가 빨간색으로 칠한 칸은 다시 뽑을 컷(새 생성)이지 edit이 아니다(10-31 정정)]`

## 2. video_edit 특성 (AICRON 웹앱, 11-04 실사용)

- AICRON MCP에는 영상 입력 칸이 없어 AI가 직접 못 돌린다. 사용자가 웹앱에서. AI는 입력 영상(고칠 구간만 자른 것)·첨부 이미지·프롬프트를 다운로드 아티팩트로 준비.
- 길이·비율은 입력 영상을 따른다(duration, aspect_ratio 무시). **과금도 입력 길이 기준, 초 단위로 올림**(1.5초 → 2초, 1080p 220 Crons). 그래서 고칠 구간만 잘라 넣고, 3.21초를 3.00초로 잘라 1초분을 아낀다.
- 입력 4초 미만도 된다. 결과는 원본 길이 뒤에 마지막 프레임이 멈춘 채 4초까지 채워진다 → 원본 길이만큼 잘라 쓴다.
- 결과 길이가 원본보다 조금 짧을 수 있다(7.54 → 7.39초, 4프레임). 편집에서 맞춘다.
- 이미지 첨부는 받는다(1장, 4장 모두). 입력 영상은 @video, 이미지는 @image1부터.
- **여러 이미지를 컷마다 나눠 배정하지 못한다.** 4컷 영상에 접시 4장을 순서대로 배정하자 1·2컷만 맞고 3컷부터 한 칸씩 밀렸고 컷 경계도 0.08~0.16초 앞당겨졌다. 컷마다 영상을 잘라 이미지 1장씩.
- **참고 이미지의 밝기·선명도·크기를 글보다 강하게 따른다.** 고르게 밝은 시트로 뒷벽을 바꾸자 벽이 인물만큼 밝고 선명·가깝게 그려져 붙여 넣은 듯 나왔다. 원본 프레임 기준 밝기(인물보다 한두 단 어둡게)·초점·녹과 때·거리·크기(화면의 몇 분의 몇)를 적고, 가능하면 원본 프레임 위에 코드로 합성한 그림을 참고로. 자른 그림 가장자리 잔여물은 지우고 넣는다.
- 한 영상 안에 하드컷이 있으면 전체 edit도 숏별로 나눠 돌린다.
- 소리: generate_audio 기본 true, 원래 소리 유지 여부 미확인 → 편집에서 원본 오디오를 쓴다. 음악 금지 문장은 그대로.
- 미확인: 입력 최대 길이(30초 넘으면 나눈다), video_extension 모드(앞뒤 늘리기, 안 써 봄).

## 3. edit 프롬프트 구조 (사용자 11-05 지시)

```
Edit @video.
1. <수정사항: 무엇이 무엇으로, 옛 상태 이름도 같이>
2. ...
(셋 이하)
Apart from these changes, nothing else may be changed, modified or added.
```

- **앞머리에 유지 목록을 길게 늘어놓지 않는다.** "Keep everything exactly ... in every frame"을 먼저 나열한 edit은 원본과 똑같이 나왔다. 유지는 끝 한 문장으로.
- 수정사항 밖의 보조 효과(배경 바람 등)는 넣지 않는다.
- 항목마다 구체적으로: 옛 상태 이름("It is not porcelain or ceramic"), 레퍼런스 번호, 재질·두께·색·원본 프레임 기준 밝기·크기. 음식은 무엇만 있고 무엇은 없는지. 입력 영상에 있는 바꿀 대상을 직접 이름 붙여("Replace the soup and any other food in the input video with ..."), AVOID에도(no soup, no broth).
- 질감을 바꿀 때만 `LOOK` 항목에 STYLE 원문 + 앞에 "replacing any stop-motion, clay, felt or puppet look and any stepped frame-by-frame motion with smooth motion"(edit은 옛 질감이 입력에 있으니 이 경우에만 옛 질감 이름을 적는다). 얼굴이 바뀔 위험이 있으니 수정 항목 하나로 얼굴 유지 + 얼굴 핵심 규칙 + 손("lean adult hands with long thin fingers").
- 옛 구조(EDIT TASK 유지 목록 → 항목 → KEEP THE PEOPLE → CONSISTENCY → AVOID)는 쓰지 않는다.

### 첨부 기준
- 입력 영상 1개(고칠 구간만).
- 바꿀 대상의 레퍼런스만.
- 질감을 바꿀 때 얼굴이 흔들리지 않게 주인공 시트 1장.
- 배경 시트는 넣지 않는다(공간은 입력 영상이 정하고, 넣으면 구도가 끌린다).
- 조명 기준 그림을 넣을 때는 "구도·건물 모양 따르지 말 것"을 네 곳에(05 문서 6절 15번).

### 결과 검수
입력 영상과 나란히 프레임으로 비교.
- 컷 타이밍·카메라가 그대로인지(edit이 컷을 합치거나 길이를 바꾸지 않았는지)
- `[예외: FACE RULE]` 검은 얼굴에 코·입·피부가 생기지 않았는지, 눈 모양
- 손 모양(통통해지지 않았는지), 손가락 개수
- 바꾼 소품·음식이 모든 컷에서 같은지
- 질감이 스톱모션·미니어처로 남지 않았는지, 동작이 끊기지 않는지
- 안 된 항목만 다시 edit. 여러 번 거듭하면 질감이 쌓이니 가능하면 원본 입력에서 다시.

## 4. 업스케일

### 왜 480p로 뽑고 나중에 올리나
- 같은 시드로 해상도만 바꿔 다시 뽑으면 구도부터 다른 영상(초안→최종 프레임 상관 0.95~0.99 vs 같은 시드 별도 작업 0.257, Segmind 실측). 이미 뽑은 클립을 그대로 1080p로 다시 뽑는 길은 AICRON MCP에 없다(seed·draft 인자 없음). Higgsfield Draft Mode(480p 초안 → 1080p 재렌더, 약 18% 비쌈)는 크레딧이 없어 안 쓴다. `[예외: 크레딧 사정]`
- 그래서: 480p로 생성하고 Higgsfield Artemis 2K로 업스케일한다(사용자 11-06 결정). 옛 규칙 "1080p가 필요한 컷은 처음부터 1080p"는 폐기.

### 설정 (Higgsfield 웹앱 Topaz Video, 11-04 확정) `[예외: 사용 서비스]`
- 프리셋 **Artemis**, 프레임 속도 **원본**, 해상도 **2K**(결과 2048×1152). 1K와 2K는 같은 5크레딧, 4K부터 비쌈. 1080 입력은 1K 거부.
- **입력은 480p 원본(854×480), `video/<씬>/raw/`.** 편집기에서 1080으로 내보낸 파일은 실제 정보가 480p라(PSNR 45dB) Artemis가 거의 못 올린다. 선명도(라플라시안 분산) 1080 내보낸 판 입력 7.4 vs 480p 원본 입력 71.4, 약 10배.
- **컷이 있는 클립은 숏별로 잘라 올린다.** fps "원본"이어도 보간 모델(apo-8)이 같이 돌아 하드컷을 건너 앞뒤 숏이 섞인 프레임이 생기고 컷 위치가 최대 4프레임 앞당겨진다. 컷 프레임을 1프레임 단위로 찾아 끊고 원본 해상도·fps 그대로.
- **사람 나오는 숏은 Artemis만.** Starlight Precise 2.5는 생성형이라 매끈한 CG 손을 실사 피부(모공·핏줄·주름)로 바꾸고, 청바지 박음질·핀셋 톱니처럼 없던 무늬와 흐린 라벨 자리에 또렷한 가짜 글씨를 새로 그린다. 사람 없는 숏에서만, 글씨가 생기면 편집에서 덮는다.
- AICRON 웹앱 업스케일(Topaz Auto, ByteDance)은 둘 다 24fps를 30fps로 보간한다(복제가 아니라 중간 프레임 합성). 색 태그도 unknown. 쓰지 않는다. Higgsfield MCP upscale_video의 topaz는 프리셋·fps 칸이 없어 같은 설정을 못 한다.

### 결과 검수 (받을 때마다)
1. **원본과 1:1 대조.** 프레임 수 비교, 결과를 480p로 줄여 프레임별로. 어느 프레임부터 어긋나는지, 앞·끝 어디가 빠졌는지. 실제로 한 숏은 끝 11프레임(0.46초)이 잘렸고 다른 두 숏은 그대로였다. 숏마다 확인.
2. **생성 길이로 짐작하지 않는다.** 같은 15초 생성본이 346, 356프레임이었고 둘 다 원본 그대로. 원본이 없으면 누락을 확정하지 않고 원본을 받는다.
3. **컷·겹침.** 화면이 크게 바뀌는 곳은 프레임을 뽑아 컷인지 빠른 이동인지. 컷이면 섞인 프레임이 없는지. 섞인 프레임 1장은 코드로 지워 고칠 수 있다.
4. **번짐·깨짐.** 빠른 손동작 번짐은 움직임 탓이면 그대로. 글씨 깨짐은 원본 같은 프레임과 비교해 업스케일이 만든 것인지 가린다. 원본 없이 원인을 말하지 않는다.

## 5. 편집용 변환 (ProRes 422 HQ)

- 이유: Topaz 결과는 HEVC 10bit라 프리미어 하드웨어 디코딩에서 네모 조각이 엉뚱한 자리에 떠 보인다(파일 자체 프레임은 깨끗). 색 태그 unknown이라 색이 죽어 보이는 것도 같이(화소값은 원본과 거의 같다 → 태그 해석 문제).
- 명령:
  ```
  ffmpeg -i 입력.mp4 -c:v prores_ks -profile:v 3 -pix_fmt yuv422p10le -vendor apl0 \
    -color_primaries bt709 -color_trc bt709 -colorspace bt709 -c:a pcm_s16le 출력_prores422hq.mov
  ```
  해상도·fps·프레임 수는 바꾸지 않는다. 변환 뒤 ffprobe로 profile HQ, bt709 세 태그, 프레임 수 확인.
- 음성이 영상보다 짧을 때 `-shortest`는 끝 프레임을 자른다 → `-af apad -shortest`로 변환하고 프레임 수 확인(11-06).
- 저장: 같은 씬 폴더 아래 `prores/`에 `원래이름_prores422hq.mov`. 2K 15초 약 360MB(약 25MB/초).
- 공유 폴더 첨부는 약 400MB까지. 넘으면 ProRes는 인트라라 `-c copy`로 반 나눔(part1 `-t`, part2 `-ss` 출력쪽), framemd5로 경계 프레임 일치 확인(11-06).
- `[예외: 사용자 PC]` PC PATH에 ffmpeg 없음 → Blender 내장 FFmpeg(`D:\Plating\prores\to_prores.py`). PC판 결과는 클라우드판보다 크다(963MB vs 661MB).
- 프리미어: 2K를 1920×1080 시퀀스에 넣으면 가장자리 약 6% 잘림. "프레임 크기로 설정(Set to Frame Size)". "프레임 크기로 비율 조정(Scale to Frame Size)"은 미리 줄여 화질이 떨어진다. 재생이 뭉개 보이면 재생 해상도 Full. HEVC를 그대로 써야 하면 환경 설정 > 미디어 > 하드웨어 가속 디코딩 끄기.
